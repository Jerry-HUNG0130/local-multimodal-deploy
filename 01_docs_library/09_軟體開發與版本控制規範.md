# 軟體開發與版本控制規範

## 第一章 總則
### 第 1 條 目的
為統一研發團隊（包含後端、前端、AI 演算法與 SRE 團隊）之開發標準，降低程式碼衝突與維護成本，並建立高效率的 CI/CD (持續整合/持續部署) 流程，特訂定本專案開發與版本控制規範。

### 第 2 條 適用範圍
凡參與本公司任何軟體專案（包括但不限於：內部核心系統、視覺通訊引擎、機房異常 RAG 知識庫系統等）之所有專案經理與開發工程師，皆必須遵守本規範。

## 第二章 git 版本控制與分支策略
### 第 3 條 分支命名原則
本公司專案一律採用簡化版 Git Flow 作為標準策略，分支命名必須具備識別性：
1. `main` 分支：唯一代表「正式生產環境 (Production)」之穩定版本。任何開發者**嚴禁**直接向 main 分支提交 (Commit) 程式碼。
2. `develop` 或 `staging` 分支：作為測試與預備上線的整合分支。
3. `feature/` 分支：開發新功能使用，例如 `feature/yolo-temperature-detection`。
4. `hotfix/` 分支：用於修復正式環境或機房監控系統的緊急阻斷性 Bug（例如漏發 Slack 警告），例如 `hotfix/slack-alert-fail`。

### 第 4 條 Commit Message 撰寫規範
提交紀錄應保持語意清晰，嚴禁使用如 "update", "fix bug", "test" 等無意義字眼。必須以動詞開頭，並簡單說明變更原因，格式建議如下：
* `[Add] 實作機房高溫 28 度 Slack 警報邏輯`
* `[Fix] 修正 YOLO 視覺引擎在低光源下無法辨識紅燈的錯誤`
* `[Refactor] 重構 RAG 知識庫之向量檢索模組，縮短查詢時間`

## 第三章 開發流程與部署
### 第 5 條 Code Review 審查機制
所有完成開發的 `feature` 分支，欲合併回 `develop` 或 `main` 前，必須在 GitHub / GitLab 上發起 Pull Request (PR)。
1. 每個 PR 至少需由一位資深工程師或同僚（Reviewer）進行程式碼審查並給予 Approve 方可合併。
2. 審查重點包含：是否存在安全漏洞（如：直接將 API Key 或 `.env` 寫入程式）、效能是否過度消耗記憶體、以及是否遵守 SOLID 物件導向原則。

### 第 6 條 自動化測試與 CI/CD
1. 任何提交的程式碼皆須在編譯伺服器通過自動化的單元測試（Unit Test）。測試覆蓋率（Coverage）不得低於 75%。
2. 若為機房監測或核心警告模組，必須另外通過整合測試（Integration Test），模擬各種異常影像輸入（如高溫、伺服器紅燈）以確保告警流程未被中斷。
